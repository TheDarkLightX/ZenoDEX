# UPBA Tau Tables Integration Design Spec

This document specifies how UPBA bounded price-grid optimality should integrate
with Tau Tables once table support exists. It is written as a bridge plan between
three layers:

- Python/Rust functional core: computes and verifies arithmetic-heavy candidate
  scores.
- Lean: proves the bounded-grid completeness and optimality bridge.
- Tau Tables: records and validates finite facts, commitments, and boolean proof
  rails.

The key constraint is current Tau Lang arithmetic. Tau should not be asked to
recompute CPMM scoring, fee rounding, ratio reduction, canonical JSON hashes, or
large integer products until the language/runtime clearly supports those safely.
The design therefore uses a host-computes/Tau-validates split.

## Goal

The current Lean theorem establishes:

```text
winner feasible in bounded grid
and upper-bound certificate checks over scoreAt(priceGrid)
-> winner globally weakly optimal over all candidates generated by bounded grid prices
```

Tau Tables should make the runtime side of this theorem checkable by providing a
canonical finite table for:

```text
scoreAt(priceGrid(maxNum, maxDen))
```

The table is exact over the configured finite grid. It does not claim optimality
over unbounded rational prices or over a grid resolution that governance did not
select.

## Feasibility Assessment

This is feasible if Tau Tables support these table-level operations:

- row existence by primary key;
- uniqueness by primary key;
- finite row count checks;
- table-root or canonical-row commitment input;
- universal checks over row flags, or host-supplied aggregate flags that Tau can
  combine fail-closed.

This is not feasible as a Tau-only math verifier if Tau Tables only provide row
storage and Tau Lang still cannot express or efficiently evaluate:

- CPMM output formulas;
- fee truncation and dust accounting;
- canonical hashing;
- large cross-multiplied inequalities;
- pairwise dominance over large tables.

The first production shape should keep those computations in the functional core
and expose boolean facts to Tau.

## Runtime Architecture

The settlement path should use four artifacts.

```text
UPBA certificate
  actual clearing certificate used to build settlement

Candidate table
  one row per bounded grid price after deterministic scoring

Completeness witness
  facts proving the candidate table corresponds to the configured grid

Optimality certificate
  winner id, volume upper bound, surplus upper bound, and table root binding
```

The trust boundary is:

```text
HostArithmeticOK
and TauTableFactsOK
and LeanTheoremApplies
-> BoundedGridGlobalWeakOptimalityOK
```

HostArithmeticOK is checked by Python/Rust deterministic verifier code. Tau
combines the facts and rejects missing or inconsistent rails.

## Table Schemas

### `UPBA_PriceGridConfigV1`

One row per settlement certificate.

| Column | Type | Meaning |
| --- | --- | --- |
| `settlement_id` | bytes32/string | Domain-separated settlement/certificate id. |
| `pool_id` | string | Pool being cleared. |
| `policy_id` | string | Must equal the UPBA policy being certified. |
| `max_price_num` | uint | Inclusive grid numerator bound. |
| `max_price_den` | uint | Inclusive grid denominator bound. |
| `score_function_id` | string | Deterministic scorer version. |
| `candidate_table_root` | bytes32/string | Canonical commitment to candidate rows. |
| `row_count` | uint | Expected row count. |

The Python v1 verifier keeps boolean gates in a separate Tau-facing fact packet
rather than in the config object. Tau Tables may store those facts beside the
config row if that is more natural once table syntax lands.

The expected row count is:

```text
(max_price_num + 1) * (max_price_den + 1)
```

This multiplication should be checked in host code unless Tau Tables have safe
bounded arithmetic for it.

### `UPBA_CandidateGridV1`

Primary key:

```text
(settlement_id, price_num, price_den)
```

Rows:

| Column | Type | Meaning |
| --- | --- | --- |
| `settlement_id` | bytes32/string | Links to config row. |
| `price_num` | uint | Candidate price numerator. |
| `price_den` | uint | Candidate price denominator. |
| `candidate_id` | bytes32/string | Hash of settlement id, price, scorer id, and score. |
| `valid_price_ok` | bool | Price passes configured filters, such as positive denominator. |
| `score_recomputed_ok` | bool | Host recomputed the row score from deterministic scorer. |
| `volume` | uint | Candidate matched volume. |
| `surplus` | uint | Candidate surplus score. |
| `winner_row_ok` | bool | True only for the winner row. |
| `dominated_by_winner_ok` | bool | Host proved winner objective dominates this row. |

The table should include every raw bounded grid pair. Invalid price rows remain
present with `valid_price_ok = false`, `volume = 0`, and `surplus = 0`, unless a
later theorem proves a reduced/filtered grid is complete. Raw-grid inclusion is
simpler and safer for v1.

### `UPBA_OptimalityWitnessV1`

One row per settlement certificate.

| Column | Type | Meaning |
| --- | --- | --- |
| `settlement_id` | bytes32/string | Links to UPBA certificate. |
| `uniform_batch_certificate_hash` | bytes32/string | Existing UPBA cert hash. |
| `candidate_table_root` | bytes32/string | Must match config row. |
| `winner_candidate_id` | bytes32/string | Existing bound optimality winner id. |
| `winner_price_num` | uint | Winner row key. |
| `winner_price_den` | uint | Winner row key. |
| `volume_upper` | uint | Winner volume and upper bound. |
| `surplus_upper_at_winner_volume` | uint | Winner surplus and upper bound. |
| `table_complete_ok` | bool | Candidate table complete under configured bounds. |
| `certificate_bound_ok` | bool | Existing optimality cert checks. |
| `global_grid_optimality_ok` | bool | Host-side composition of all required checks. |

Tau should require all booleans to be true before allowing the settlement to
claim bounded-grid global weak optimality.

## Canonical Commitments

The candidate table root must be computed over canonical rows sorted by:

```text
(settlement_id, price_num, price_den)
```

Recommended candidate id body:

```json
{
  "schema": "zenodex/upba_price_grid_candidate_id/v1",
  "settlement_id": "...",
  "score_function_id": "...",
  "price_num": 1,
  "price_den": 2,
  "valid_price_ok": true,
  "volume": 100,
  "surplus": 40
}
```

Recommended table root body:

```json
{
  "schema": "zenodex/upba_price_grid_table/v1",
  "settlement_id": "...",
  "max_price_num": 128,
  "max_price_den": 128,
  "score_function_id": "zenodex/upba_price_grid/full_fill_exact_in_limit/v1",
  "rows": [
    {
      "schema": "zenodex/upba_price_grid_row/v1",
      "settlement_id": "...",
      "price_num": 1,
      "price_den": 2,
      "candidate_id": "...",
      "valid_price_ok": true,
      "score_recomputed_ok": true,
      "volume": 100,
      "surplus": 40,
      "winner_row_ok": false,
      "dominated_by_winner_ok": true
    }
  ]
}
```

The exact canonical encoding should reuse the existing ZenoDEX canonical JSON or
a future binary wire format. Tau should receive the resulting roots and boolean
facts, then check consistency of those facts.

## Tau Policy Shape

Tau should be used as a boolean policy gate. The host supplies one-hot or sbf
facts derived from table verification.

Required inputs:

```text
has_upba_certificate
has_candidate_table
has_optimality_witness
policy_id_ok
table_root_matches_certificate
row_count_ok
grid_complete_ok
scores_recomputed_ok
winner_binding_ok
winner_feasible_ok
dominance_ok
certificate_bound_ok
no_unknown_rows_ok
all_required_roots_bound_ok
```

Tau accept condition:

```text
accept :=
  has_upba_certificate
  and has_candidate_table
  and has_optimality_witness
  and policy_id_ok
  and table_root_matches_certificate
  and row_count_ok
  and grid_complete_ok
  and scores_recomputed_ok
  and winner_binding_ok
  and winner_feasible_ok
  and dominance_ok
  and certificate_bound_ok
  and no_unknown_rows_ok
  and all_required_roots_bound_ok
```

This is intentionally simple. Current Tau Lang should combine these flags rather
than recomputing the arithmetic behind them.

## Host Verifier Obligations

The host verifier must check these conditions before setting Tau flags.

### Grid Coverage

For configured bounds:

```text
0 <= price_num <= max_price_num
0 <= price_den <= max_price_den
```

Host checks:

```text
row_count == (max_price_num + 1) * (max_price_den + 1)
primary keys are unique
every bounded key exists
no key outside bounds exists
```

This corresponds to Lean theorem `priceGrid_complete`.

### Score Binding

For every row:

```text
row == scoreAt(price_num, price_den)
```

The host recomputes score using deterministic integer code and checks:

```text
score_function_id matches deployed code version
row.volume matches recomputed volume
row.surplus matches recomputed surplus
row.candidate_id matches recomputed candidate id
```

Tau receives `scores_recomputed_ok`.

### Winner Binding

The winner row must bind to the actual UPBA certificate:

```text
winner_candidate_id = candidate_id_for(uniform_batch_certificate_hash)
```

The current Python verifier already checks this for the finite audited-set
certificate. The Tau-table extension should bind the same winner id to the row
key and table root.

### Dominance

For each valid row:

```text
row.volume <= winner.volume
and if row.volume = winner.volume then row.surplus <= winner.surplus
```

Host sets `dominated_by_winner_ok` per row and `dominance_ok` globally.

### Completeness Composition

Host sets `global_grid_optimality_ok` only when:

```text
grid_complete_ok
and scores_recomputed_ok
and winner_feasible_ok
and dominance_ok
and certificate_bound_ok
```

Tau can independently require the component flags as well as the aggregate flag.
This catches missing wiring mistakes.

## Lean Binding

The current Lean names are:

- `Price`
- `PriceInGridBounds`
- `priceGrid`
- `priceGridCandidates`
- `FeasibleGridCandidate`
- `priceGrid_complete`
- `priceGridCandidates_complete`
- `priceGridCandidates_complete_audit_set`
- `price_grid_upper_bound_certificate_implies_global_weak_optimal`

The intended bridge is:

```text
TauTableComplete(table, maxNum, maxDen)
RowsEqualScoreAtGrid(table, scoreAt)
WinnerFeasible(table, winner)
WinnerDominatesRows(table, winner)
-> GloballyWeaklyOptimal winner (FeasibleGridCandidate maxNum maxDen scoreAt)
```

`TauTableComplete` and `RowsEqualScoreAtGrid` are runtime evidence predicates.
Lean proves that if those predicates correspond to the model definitions, the
bounded-grid global optimality conclusion follows.

## Implementation Plan

### Phase 0: Current State

Status: done.

- Lean proves bounded price-grid completeness.
- Python verifies audited-set optimality and winner binding.
- DEX engine accepts optional optimality evidence.

### Phase 1: Python Table Verifier

Status: implemented in `src/core/uniform_batch_price_grid_table.py`.

Add:

```text
src/core/uniform_batch_price_grid_table.py
```

Responsibilities:

- parse `UPBA_PriceGridConfigV1`;
- parse candidate rows;
- recompute row scores;
- verify primary-key coverage;
- verify table root;
- verify winner dominance;
- emit Tau-facing boolean fact packet.

Add tests:

```text
tests/core/test_uniform_batch_price_grid_table.py
```

Required negative cases:

- missing grid key;
- duplicate grid key;
- out-of-bounds row;
- score mismatch;
- table-root mismatch;
- winner row missing;
- invalid certificate fill binding;
- dominance flag inconsistent with row scores.

The implemented v1 scorer is intentionally narrow: single-pool CPMM,
`SWAP_EXACT_IN`, UPBA v1 full-fill certificate semantics, and full-fill-or-reject
candidate scoring for each bounded integer price pair. The table verifier calls
the existing UPBA certificate verifier before accepting the grid witness, so the
table cannot upgrade an invalid settlement certificate.

### Phase 2: Tau Table Contract Draft

Once Tau Tables syntax is available, add a draft spec such as:

```text
src/tau_specs/recommended/upba_price_grid_table_gate_v1.tau
```

The Tau spec should only combine host facts unless Tau Tables safely support the
needed arithmetic. The first version should reject if any required fact is false
or missing.

### Phase 3: Engine Attachment

Extend settlement envelope with:

```text
uniform_batch_price_grid_table
uniform_batch_price_grid_witness
```

Engine checks:

```text
if price_grid_witness is present:
  require uniform_batch_certificate
  require optimality_certificate
  verify table root and witness
  pass boolean fact packet to Tau gate
```

The existing optional optimality certificate remains valid for audited-set
claims. The table witness upgrades the claim to bounded-grid global weak
optimality.

### Phase 4: Claim Registry

Add a scoped claim only after Phase 1 and Phase 3 tests pass:

```text
id: upba:bounded_price_grid_global_weak_optimality
scope: single-pool exact-in UPBA over configured bounded integer price grid
status: supported_by_runtime_and_lean
non_claims:
  - unbounded rational price optimality
  - fair order inclusion
  - exact-out, multi-hop, LP actions
  - oracle or mark-price safety
```

## Open Design Choices

### Raw Grid vs Reduced-Ratio Grid

Raw grid is recommended for v1:

```text
all pairs 0 <= num <= maxNum, 0 <= den <= maxDen
```

Reduced-ratio grid is smaller, but it needs another completeness theorem:

```text
every raw ratio has an equivalent reduced representative
```

That theorem is useful, but it should be a v2 optimization after the raw-grid
path is working.

### Zero Denominator Rows

Include zero-denominator rows as invalid rows in the raw table for v1. This
preserves simple coverage. The scorer marks them invalid and gives zero score.
A later positive-price-grid theorem can remove them safely.

### Grid Size

Naive table size is:

```text
(maxNum + 1) * (maxDen + 1)
```

This can become large. Production should start with small configured bounds or a
threshold-price table generated from order limits. A threshold table can be much
smaller, but it needs a separate Lean theorem proving threshold representatives
cover all objective-changing price regions.

### Tau Arithmetic Upgrade Path

If Tau Tables eventually support safe bounded arithmetic, move these checks from
host facts into Tau gradually:

1. row-count arithmetic;
2. row bounds;
3. dominance checks over integer columns;
4. simple candidate-id/table-root relation if hashing is available;
5. never move CPMM scoring until integer semantics and performance are fully
   specified.

## Acceptance Checklist

A Tau Tables integration is ready for promotion only when all items pass:

```text
Python table verifier has focused positive and negative tests.
Tau gate rejects every missing or false required fact.
Candidate table root is bound to the UPBA certificate and optimality witness.
Lean proof command passes.
No placeholder/trust scan findings in touched Lean files.
Engine tests cover accepted table witness and malformed witness rejection.
Docs state bounded-grid scope and non-claims.
```

## Non-Claims

This design does not claim:

- Tau can currently perform CPMM scoring;
- Tau can currently hash canonical rows;
- bounded grid optimality equals unbounded rational optimality;
- the chosen grid resolution is economically sufficient;
- UPBA removes inclusion, oracle, or batch-boundary games.

The specific target claim is:

```text
Given a configured bounded integer grid and a deterministic scorer,
if the table contains exactly every scored grid candidate and the winner
dominates that table, then the winner is globally weakly optimal over that
bounded grid-generated family.
```
