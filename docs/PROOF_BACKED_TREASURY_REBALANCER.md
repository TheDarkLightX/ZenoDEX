# Proof-Backed Treasury Rebalancer

This document defines the first non-live design for protocol-owned market
making in ZenoDEX. The intended role is not to trade against users with
privileged discretion. The role is to admit only public, bounded, auditable
treasury rebalancing opportunities that improve market quality or capture
available edge for the protocol.

The safer name is **Treasury Rebalancer**, not "protocol market maker". It is a
rule-bound treasury strategy with public receipts, hard caps, and fail-closed
admission checks.

## Why It Exists

Every AMM creates arbitrage and market-making opportunities. That is normal:

- arbitrage aligns pool prices with external prices,
- market makers absorb inventory risk and improve liquidity,
- solvers compete to find better routes and clearing prices,
- batch auctions can redirect surplus away from toxic MEV and toward users,
  solvers, and protocol revenue.

The protocol should not try to remove all arbitrage. It should remove the
disaster states:

- stale-oracle extraction,
- user sandwiching,
- private order-flow abuse,
- treasury inventory blowups,
- wash volume that farms rewards,
- hidden discretionary trading by protocol insiders.

## Admission Contract

A treasury trade is admissible only if all of the following checks pass:

```text
TradeAllowed :=
  OracleFresh
  and PublicRoute
  and NoUserSandwich
  and NoPrivateOrderflow
  and NoSelfTrade
  and ExpectedEdge >= Costs + RiskBuffer
  and TradeSize <= LiquidityBudget
  and InventoryAfter <= MaxInventory
  and DailyLossUsed + WorstCaseLoss <= DailyLossBudget
  and CooldownElapsed
  and not Paused
```

In plain English: the bot may trade only when the price source is usable, the
route is public, it is not exploiting user flow, the expected edge clears all
costs and buffers, and the treasury remains inside explicit loss and inventory
budgets.

## Revenue Flow

Treasury strategy revenue should be accounted as verified value, not as a
promise:

```text
NetTreasuryEdge :=
  RealizedPnL
  - GasCost
  - VenueFees
  - SlippageCost
  - InventoryReserveIncrease

Distributable <= VerifiedValueGained + ExplicitBudget
```

In plain English: only realized, auditable value can feed buyback, burn,
rewards, bounties, or staking rewards. A budget can subsidize bootstrapping,
but it must be explicit and capped.

This matches the existing FIRE/tokenomics proof posture: reward, rebate,
buyback, bounty, and treasury spend are admissible only when bounded by
verified value plus explicit budget.

## Strategy Classes

### 1. Public Internal Arbitrage

The bot can correct price drift between ZenoDEX pools when:

- both pool states are public,
- route simulation is deterministic,
- stale oracle and stale reserve checks pass,
- no pending user order is used as privileged information,
- expected edge remains positive after risk buffer.

This should eventually compose with `arbitrage_bounds_v1.tau`, which already
models bounded arbitrage as healthy price discovery while limiting extraction.

### 2. External Price Rebalancing

The bot can rebalance ZenoDEX inventory against external venues only when:

- oracle snapshots are fresh,
- external execution venues are allowlisted and monitored,
- inventory caps are tighter than internal-only arbitrage caps,
- the bot does not custody user funds,
- the receipt records source venue, quote, execution, and realized PnL.

This is higher legal and operational risk than internal arbitrage, so it should
ship later.

### 3. Batch Auction Surplus Capture

For intent batches, the best design is solver competition:

- solvers bid for the right to clear a batch,
- users receive at least their limit,
- solver reward is explicit,
- remaining surplus becomes protocol fees or user improvement,
- canonical tie-breaking prevents discretionary winner selection.

This is preferable to a privileged treasury bot because independent solvers
compete and the protocol captures surplus through rules instead of hidden
trading.

### 4. Protocol-Owned Liquidity

The treasury may own LP positions, but this must be budgeted as inventory risk:

- pool exposure cap,
- asset exposure cap,
- impermanent-loss budget,
- withdrawal cooldown,
- no reward multiplier for self-owned wash volume.

Protocol-owned liquidity is useful for launch liquidity, but it can become a
subsidy sink if rewards are based on raw volume instead of verified external
value.

## User Experience

Users should experience:

- tighter spreads,
- deeper liquidity,
- fewer toxic MEV outcomes,
- clearer receipts for protocol revenue,
- more sustainable buyback/burn or reward flows.

Users should not experience:

- the protocol front-running them,
- unexplained treasury losses,
- hidden routing conflicts,
- a bot with privileged access to pending orders,
- rewards generated by circular self-trading.

## Disaster-State Controls

| Disaster State | Control |
| --- | --- |
| Bot sandwiches users | `NoUserSandwich`, public route requirement, delayed/shadow receipts |
| Bot uses private order flow | `NoPrivateOrderflow`, no privileged mempool source |
| Bot drains treasury on stale prices | `OracleFresh`, price-divergence caps, kill switch |
| Bot accumulates toxic inventory | `InventoryAfter <= MaxInventory` |
| Bot loss exceeds daily budget | `DailyLossUsed + WorstCaseLoss <= DailyLossBudget` |
| Bot wash-trades to farm rewards | self-flow excluded from reward/value metrics |
| Bot becomes discretionary trading desk | deterministic strategy classes and public receipts |
| Bot crowds out public keepers | public solver auction first; treasury bot caps lower than public opportunity set |

## Launch Sequence

1. **Shadow mode**
   - Bot observes opportunities and emits receipts.
   - No trades.
   - Compare expected edge to hypothetical realized edge.

2. **Public solver competition**
   - Keepers and solvers compete for arbitrage/settlement opportunities.
   - Protocol collects deterministic fees or surplus share.

3. **Tiny treasury rebalancer**
   - Only internal public routes.
   - Low notional caps.
   - Daily loss budget close to zero.
   - Full receipts.

4. **External venue expansion**
   - Only after legal review and venue risk review.
   - Separate keys, separate risk caps, separate monitoring.

5. **Protocol-owned liquidity**
   - Treat as a treasury asset allocation, not as guaranteed yield.
   - Cap reward eligibility for protocol-owned volume.

## Current Non-Live Evidence Hook

The companion offline ESSO model is:

```text
src/kernels/dex/treasury_rebalancer_guard_v1.yaml
```

It models the admission guard and budget invariants only. It is not wired into
runtime execution. It is a first proof/evidence target for the strategy:

- admitted trades preserve daily loss budget,
- admitted trades preserve inventory cap,
- admission requires public/non-abusive route flags,
- admission requires edge to dominate cost plus risk buffer,
- governance policy changes cannot set risk budgets above treasury balance.

Local verification status:


## Non-Claims

This design does not claim:

- guaranteed profit,
- legal approval,
- public-market execution safety,
- protection against every oracle failure mode,
- production readiness of an autonomous treasury bot.

The current claim is narrower: a protocol-owned rebalancer can be designed as a
bounded, public, receipt-producing strategy whose spend and risk are constrained
by explicit budgets before any live integration.
