tau> # ============================================================================

tau> # NEW TABLE KIND 3 - THE GUARDED ESCROW TABLE (conservation that is a guard)

tau> # ============================================================================

tau> # exp2 proves "conservation under transfer" as

tau> #   (c.alice = b.alice - d && c.bob = b.bob + d) -> c.alice+c.bob = b.alice+b.bob

tau> # That is TRUE for every d, with no hypothesis at all - it is the ring

tau> # identity (x-d)+(y+d) = x+y in Z/256. It is a theorem about arithmetic, not

tau> # a safety property of a balance table, and it holds exactly where the table

tau> # is least safe: at d = 250 on a balance of 10 the sender's cell goes 10 ->

tau> # 16 and the receiver's 5 -> 255, minting 256 units, while the sum is

tau> # preserved mod 256. See opus_attack_exp2_wraparound.tau.

tau> #

tau> # A balance table kind therefore has to carry its guards as part of the

tau> # schema contract, and the conservation claim has to be stated jointly with

tau> # monotonicity - "no cell moved the wrong way" - which is what actually

tau> # fails at the wrap boundary. Three cells, one move:

tau> #

tau> #   GUARD  :  d <= e.user     (sufficiency: no underflow)

tau> #          &  e.escrow <= 255 - d   (capacity: no overflow; 255-d does not

tau> #                                    itself wrap, which is why it is written

tau> #                                    this way and not as e.user+e.escrow<=255)

tau> #   MOVE   :  f.user = e.user - d,  f.escrow = e.escrow + d,  f.vault = e.vault

tau> #

tau> # ZenoDEX surface: any two-table value movement - deposit/withdraw, escrow

tau> # lock/release, vault rebalancing - where the pair of tables must conserve

tau> # AND no participant may gain from the move.

tau> # Run: tau -q < opus_new3_guarded_escrow_table.tau

tau> # EXPECTED-RESULTS: T F T T

tau>
